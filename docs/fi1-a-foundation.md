Sign-out calls `POST /auth/logout`, then clears memory, the query cache and the branch context, and tells the other tabs (BroadcastChannel), which show "You signed out in another tab." If the server cannot be reached on load, the page says so and offers to try again. `/me` is refetched when the user returns to the tab after 10 s, so permission and branch changes show promptly. |

On `BRANCH_SCOPE_DENIED` it is cleared, a notice says so, and it is not chosen again automatically (the user may choose it deliberately). Changing it reloads server state other than `/me`. |
| **FI1-A-D8 Idempotency-key lifecycle** | `lib/api/idempotency.ts`: a key belongs to one logical command (type, resource, body). An unchanged command keeps its key, across network retries and across resubmission after a 412. A changed command (decision, reason, text, values or `step_id`) gets a new one. A 412 never creates a key. `reset()` after success. `sendCommand` retries only when no response arrived (two retries), always with the same key and body; any answered refusal goes back to the caller. No screen uses it yet; FI1-B is the first. |

## Findings

- **FI1-A-F1: the operator commands can give a user only one branch. Coverage limitation / deferred provisioning capability; NON-BLOCKING.** `onboard_pilot_user` refuses a second default branch, and no other command adds branch access. So the live environment has only single-branch users: choosing among several branches is proven by unit and component tests, not against the real backend. Not a blocker for FI1; relevant when real users cover several branches.
- **FI1-A-F2: a Vite dev server for this repository had been running on 127.0.0.1:3000 since 2026-10-01** (mock mode, from an earlier session). Local development housekeeping; NOT A PRODUCT DEFECT. The FI1-A runs used port 3100; the old process was stopped at closure (no rerun needed).

- **FI1-A-F3: without Web Locks, tabs restoring at once end the session. Development-environment finding, not a production defect; CONFIRMED in the live run, remedied by FI1-A-D11.** The first live run used plain-HTTP tenant names (`fi1a-alpha.internal`), and Chromium's flag for treating them as secure did not take effect (`isSecureContext` false, `navigator.locks` undefined). Three tabs opened at once each restored the session; their refreshes went out concurrently with the same cookie; the backend saw a rotated token reused and revoked the session (`auth_sessions.revoke_reason = REFRESH_REUSE`), as designed (C1-D9). The in-tab guarantee held throughout. With `*.localhost` tenant names the page is a secure context, the lock serializes the refreshes, and the same scenario passes. Production is unaffected as long as tenants are served over HTTPS, which the `Secure` refresh cookie already requires. The FI1-Q3 example is amended accordingly (ruling above).
